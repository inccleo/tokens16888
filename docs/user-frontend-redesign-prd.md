## 2. 背景与现状

当前项目基于 Sub2API，已经具备用户账号、API Key、模型调用、用量统计、余额充值、订单和管理员管理能力。

前置静态审计中识别的主要问题（其中布局与入口边界已在本轮先行修正，其余仍作为后续工作）：

1. 前置审计时用户端与管理员端共用 `AppLayout`、`AppSidebar` 和较多视觉组件；本轮已拆分布局与导航，仍需浏览器回归。
2. 用户首页偏统计后台，第一屏展示较多 Token、RPM、TPM、费用和图表，用户不容易找到“创建 Key、查看模型、充值、复制调用代码”等核心动作。
3. 当前用户菜单较长，模型、密钥、用量、充值、订单、兑换码、订阅、个人资料等功能缺少清晰分组。
4. 前置视觉体系包含较多玻璃效果、渐变和多色指标卡，数据层级不够稳定；本轮已先收敛布局底色和 Header，页面级视觉仍需梳理。
5. 管理员登录后进入管理员端是合理的，同时需要能够明确切换到用户端进行真实用户体验验证；本轮已加入双向切换入口。
6. 用户端需要从“通用后台”转向“开发者平台”：模型目录、价格、接口文档、密钥、余额和调用记录应形成连续流程。

当前主要实现位置（源码位于仓库内的 `sub2api/` 子目录）：

- `sub2api/frontend/src/router/index.ts`
- `sub2api/frontend/src/layouts/{PublicLayout,UserLayout,AdminLayout}.vue`
- `sub2api/frontend/src/components/layout/{UserSidebar,AdminSidebar,AppHeader}.vue`
- `sub2api/frontend/src/views/auth/LoginView.vue`
- `sub2api/frontend/src/views/user/{DashboardView,DocsView,KeysView,UsageView,PaymentView}.vue`
- `sub2api/frontend/src/style.css`

## 3. 产品定位

16888 用户端定位为：

> 面向开发者和团队的统一 AI API 接入控制台，用一个账户、一组 API Key 和一套计费体系接入多个模型供应商。

用户进入平台后的核心路径：

```text
注册/登录 → 浏览模型 → 查看价格与状态 → 创建 API Key → 复制调用示例 → 发起调用 → 查看用量 → 充值或调整额度
```

## 4. 项目目标

### 4.1 必须达成

- 用户端和管理员端使用独立的布局、导航和路由模块。
- 普通用户登录后进入用户控制台，管理员入口进入管理员控制台。
- 用户登录后 30 秒内可以完成创建 API Key 或开始调用模型。
- 用户能够清楚看到余额、可用模型、API 地址、Key 状态和最近用量。
- 模型、价格、文档、密钥、充值和订单形成闭环。
- 保留现有后端 API 和数据结构，优先进行前端重构。
- 旧路径继续可用，已有书签和外部链接不因重构失效。
- 支持 320px、768px、1024px、1440px 宽度。

### 4.2 非目标

- 第一阶段不拆分后端服务。
- 第一阶段不更换 Vue、Vite、Tailwind、Pinia 或 Vue Router。
- 第一阶段不直接迁移为两个独立 Git 仓库。
- 不复制 APIMart 的品牌、文案、图片或页面代码，只借鉴信息架构和交互节奏。
- 不在前端绕过后端权限校验；所有管理员接口继续由后端鉴权。
- 本次重构不新增团队/组织/子账号/多成员协作能力。第 3 节定位中的“团队”指单账户服务团队使用场景，多成员协作列为后续规划，不在本次范围。

### 5.3 管理员控制台

管理员继续使用 `/admin/*`，但使用独立 `AdminLayout`。管理员端已具备较完整的运营能力，路由按模块分组（下列为现状真实模块，重构中保留并统一到 `AdminLayout`）：

- 登录与总览：`/admin/login`、`/admin/dashboard`
- 用户与分组：`/admin/users`、`/admin/groups`
- 渠道与上游：`/admin/accounts`、`/admin/channels/*`、渠道监控、代理池
- 订单与支付：`/admin/orders/*`、支付大盘、充值套餐
- 运营与风控：运营大盘、风控、公告、订阅、兑换码
- 分销：邀请、返利、转账、记录
- 系统：`/admin/settings`、`/admin/audit-logs`、备份、插件

管理员端不复用用户导航。管理员可从管理员侧栏“用户端”或账户菜单“查看用户端”进入 `/console`，在用户壳层通过账户菜单返回 `/admin/dashboard`；账号和登录态保持不变。

管理员端的具体功能与“好用”要求见第 8 节，重构不得削弱现有管理员能力。

## 6. 认证与权限需求

### 6.1 登录入口

- `/login` 作为用户端登录入口；管理员账号从此入口完成登录后默认进入 `/console`。
- `/admin/login` 作为管理员端登录入口。
- `/login?redirect=...` 登录后回到用户目标页面。
- `/admin/login?redirect=...` 登录后回到管理员目标页面。
- 管理员账号从用户入口登录时，默认进入用户端；从管理员入口登录时，进入管理员端。已登录管理员再次打开 `/login` 时仍回到用户端，只有 `/admin/login` 对应管理员入口。
- 角色只用于权限校验，不再作为唯一的“跳转到哪个前端”的依据。

### 6.2 安全要求

- 管理员路由保留 `requiresAdmin` 前端守卫。
- 后端管理员 API 继续独立鉴权，前端守卫不能作为安全边界。
- 管理员端优先支持 TOTP、Passkey 和重新验证高风险操作。
- API Key 只在创建完成时完整展示一次，后续默认脱敏。
- 退出登录时清理用户端缓存、余额、用量和公告状态。

## 7. 用户控制台功能需求

### 7.1 用户总览 `/console`

第一屏只保留高价值信息：

1. 当前可用余额、冻结余额和充值按钮。
2. API Key 数量、活跃 Key 数量和创建按钮。
3. 今日请求量、今日费用、成功率或错误率。
4. 平台 API 连通状态和系统公告；平台连通状态不得冒充所有上游模型均健康。
5. 最近调用记录。
6. 快速开始：选择模型、创建 Key、复制 Python/cURL 示例。

CTA 层级（与阶段 2 验收对齐，消除“首屏 6 块”与“不超过 1 主 + 2 次 CTA”的冲突）：第一屏信息模块可包含以上多块，但**高强调按钮**须遵守“1 个主 CTA + 最多 2 个次 CTA”——主 CTA 为“快速开始 / 创建第一个 Key”，次 CTA 为“充值”和“查看用量”，其余为普通链接或卡片内动作，不再叠加高强调按钮。

新用户引导复用现有 `stores/onboarding.ts` 与 `useOnboardingTour`，不重复实现；“30 秒建 Key”以该引导为载体。

第二屏展示：

- 近 7 天费用趋势。
- 模型调用分布。
- 热门模型推荐。
- 平台配额和重置时间。

空状态要求：

- 没有 API Key 时显示“创建第一个 API Key”。
- 没有用量时显示“复制示例并发起第一次调用”。
- 没有余额时显示余额说明和充值入口。

### 7.2 模型市场 `/console/models`

模型列表必须支持：

- 分类：对话、推理、图像、视频、音频、Embedding。
- 搜索模型名称、供应商和能力标签。
- 显示价格单位、当前状态、响应速度等级和推荐标识。
- 显示支持的接口协议：OpenAI Compatible、Anthropic Compatible 等。
- 显示模型上下文、输入输出能力、图片/视频限制等关键参数。
- 允许收藏模型。
- 进入详情页后显示调用示例和“使用此模型”按钮。

模型详情必须能够直接跳转：

```text
模型详情 → 创建/选择 API Key → 复制示例 → 打开文档
```

### 7.3 API Key `/console/keys`

- 创建 Key 分两档：**简单模式**默认只需填名称即可创建；**高级选项**（所属分组、额度、有效期、IP 白名单、速率限制）默认折叠、按需展开，避免新用户首次建 Key 面对过多字段，保障“30 秒建 Key”。
- 列表显示：名称、前缀、状态、创建时间、最后使用时间、额度使用情况。
- 支持复制、禁用、启用、删除、编辑限制。
- 创建成功后显示一次完整 Key，并明确提示不要提交到代码仓库。
- 提供 API Base URL、一键复制配置和语言示例。
- 移动端由表格切换为卡片列表，避免横向滚动作为唯一方案。

### 7.4 用量 `/console/usage`

- 费用、请求次数、Token、成功率、平均响应时间。
- 按时间、模型、API Key、请求类型筛选。
- 区分成功、失败、处理中和未知状态。
- 支持查看请求详情和错误原因。
- 支持 CSV 导出。
- 图表和表格使用统一的金额、Token 和时间格式。

### 7.5 余额、充值与订单

余额页包括：

- 可用余额。
- 冻结余额。
- 充值套餐。
- 兑换码。
- 充值记录。
- 订单状态。

订单状态必须来自后端权威结果，不根据“提交支付请求成功”直接显示为已支付。界面至少支持：

- 待支付
- 支付中
- 已支付
- 支付失败
- 已取消
- 待确认

支付渠道交互（保留现有实现，视觉统一但逻辑不回退）：

- 支持微信二维码、Stripe、Airwallex 等多渠道收银台；收银台样式随重构统一，但支付跳转、二维码轮询、弹窗和支付结果页逻辑保留。
- 微信等异步支付支持中断后恢复（参考现有 `paymentWechatResume`），用户返回后能继续查看订单结果，刷新页面不丢失订单查询上下文。
- 支付结果以后端回调 / 查询为准，前端不得凭“发起成功”判定已支付。

余额与用量预警：

- 可用余额低于阈值时，在总览与顶部工具栏提示并给出充值入口。
- 用量或额度接近上限时提醒，避免调用被静默截断。

### 7.6 快速开始与文档

- 展示 Base URL。
- 支持 cURL、Python、JavaScript、Go、Java、PHP。
- 支持复制完整代码片段。
- 提供 OpenAI SDK、Anthropic SDK、原生 HTTP 三种入口。
- 示例中的 Key 必须使用占位符，不显示真实密钥。
- 提供“第一次调用”检查清单。

## 8. 管理员控制台功能需求

管理员端目标：**运营效率优先**。管理员端已具备较完整能力，本节针对“管理员好用”提出功能与交互要求，重构中保留现有能力并统一到 `AdminLayout`。

### 8.1 通用原则

- 独立 `AdminLayout` 与管理员导航，不复用用户端组件与视觉重心。
- 列表页统一支持搜索、筛选、排序、分页、批量操作和导出。
- 高危操作（改余额、封号、退款、改渠道、改系统设置）需二次确认，并写入审计。
- 关键运营任务应能在少步骤内完成，避免多页面来回跳转。

### 8.2 管理员总览 `/admin/dashboard`

第一屏聚焦“今天要处理什么”：

- 营收概览：今日 / 本月充值与消耗。
- 用户概览：活跃用户、新增用户。
- 待处理事项：待确认订单、待处理退款、风控告警数量，可直接进入处理。
- 渠道健康：上游渠道可用性与异常渠道数，异常可下钻。
- 系统状态：错误率、异常调用率、健康检查结果。

参考现有运营大盘（`OpsDashboard`），避免重复造盘。

### 8.3 渠道与上游账号

- 渠道监控：渠道健康状态一眼可见，异常可下钻到具体渠道与调用（`ChannelMonitorView`）。
- 上游账号池：账号优先级、调度评分、启停与批量编辑（`AccountsView`）。
- 代理池：代理可用性、凭据与筛选（`ProxiesView`）。
- 要求：批量启停、故障渠道快速定位与临时禁用，操作留痕。

### 8.4 用户与分组管理

- 用户：搜索 / 筛选、查看用量与余额、调整余额与额度、封禁 / 解封、重置、查看该用户的 Key（`UsersView`）。
- 分组：分组权限、模型可用范围与计费策略（`GroupsView`）。
- 批量操作、导出，所有余额与状态变更写入审计。
- 代客排查（impersonation，可选）：进入需二次验证、全程审计、默认只读，用于客服定位问题，不得成为绕过用户授权的通道。

### 8.5 订单、支付与对账

- 订单列表与状态流转，支持按状态、渠道、时间、用户筛选（`AdminOrdersView`）。
- **支付失败 / 待确认 / 待支付订单必须有处理入口**：手动确认、重试查询、退款。
- 对账与支付大盘以后端权威数据为准（`AdminPaymentDashboardView`）。
- 充值套餐 / 价格计划管理（`AdminPaymentPlansView`）。
- 退款与手动改单必须二次确认并写入审计。

### 8.6 风控与运营

- 风控规则与命中记录、异常调用 / 刷单检测（`RiskControlView`）。
- 告警可下钻到具体用户、Key、渠道，并支持处置（封禁、限流、标记）。
- 公告发布、兑换码、订阅管理纳入运营模块。

### 8.7 分销管理

- 邀请、返利、转账与记录（`admin/affiliates/*`）。
- 返利结算与转账留痕，金额变更写入审计。

### 8.8 系统、审计与备份

- 系统设置、公告、插件、备份（`SettingsView`、`BackupView`、`PluginsView`）。
- 审计日志（`AuditLogView`）记录所有高危操作：操作者、时间、对象、变更前后值；改余额、封号、改渠道、退款、改系统设置必须可追溯。

### 8.9 管理员权限分级（建议）

- 建议区分超管 / 运营 / 客服角色；高危操作（改余额、封号、退款、改系统设置）限超管或需二次验证。
- 前端按角色隐藏入口，后端强制校验，前端隐藏不作为安全边界。

### 8.10 管理员端验收

- 常见运营链路（查用户 → 调额度 → 确认订单 → 处理告警）可在少步骤内完成。
- 批量操作有确认与结果反馈。
- 高危操作全部有审计记录。
- 渠道故障能在总览快速定位并处置。
- 管理员端功能相较重构前不缩水。

## 9. 视觉与交互规范

### 9.1 设计方向

- 中性浅色控制台为默认基底，支持深色模式；管理端和用户端各自保持清晰的视觉层级。
- 石墨、蓝灰作为文字与边框色。
- 16888 青绿色作为唯一主强调色。
- 减少紫色、彩虹渐变和多色 KPI 卡片。
- 使用细边框、低对比面板、轻微网格纹理建立层次。
- 重要按钮使用实色，不依赖大面积渐变。

### 9.2 布局

- 公共站点使用顶部导航。
- 用户控制台使用独立用户侧边栏和顶部工具栏。
- 管理员控制台使用独立管理员侧边栏。
- 内容区域最大宽度建议 1280px。
- 表格页面在移动端转为卡片或抽屉详情。
- 关键操作不只依赖图标，必须有文字或辅助标签。

### 9.3 组件规范

- 页面有明确的标题、说明和主要操作。
- 所有按钮具备 hover、active、focus、disabled 状态。
- 数据加载使用骨架屏或结构化 loading，不使用空白页面。
- 错误信息显示在操作附近，不只依赖 Toast。
- 列表无数据时提供下一步操作。
- 弹窗优先改为抽屉或页面内编辑，复杂流程才使用 Modal。
- 金额和 Token 使用等宽数字并右对齐。

### 9.4 移动端

- 320px 宽度下登录、充值、创建 Key 可完成。
- 768px 以下侧边栏改为抽屉或底部导航。
- 顶部固定显示余额和用户菜单。
- 表格提供横向滚动和卡片视图，不截断关键操作。
- 复制、充值、创建 Key 等主要按钮保持至少 44px 点击区域。
